# Route jobs/job_applications/banners access through SECURITY DEFINER RPCs (v1)

Every direct `.from('jobs')`, `.from('job_applications')`, and `.from('banners')` call in the jobs and banners providers is replaced by an `.rpc()` call backed by a new `supabase/jobs_banners_rpc.sql` file defining 20 `SECURITY DEFINER` functions. The motivation is a PostgREST `PGRST205` stale-schema-cache error that makes those three tables unreachable through the REST table API; funnelling all reads and writes through RPCs sidesteps the cache and lets the file end with `NOTIFY pgrst, 'reload schema';` to force a reload. Authorization that RLS used to enforce is now re-implemented inside each function (admin gates via the pre-existing `is_admin()`, ownership via `auth.uid()::text`), since `SECURITY DEFINER` runs as the definer and bypasses RLS. The temporary DEBUG passthrough in `error_utils.dart` was also reverted in the same change.

Watch for: (1) **confirmed** — `update_job` and `update_banner` use `COALESCE(p_data->>'key', existing)` for text columns, so passing an explicit `null` (which the edit forms do to clear `category`, `cover_image_url`, `link_page`) no longer clears the column; the old `.update({...data})` did. This is a behavioral regression on edit, and it is inconsistent with `deadline`/`max_slots` which *can* be cleared. (2) **possible** — `has_applied_to_job(p_job_id, p_user_id)` accepts an arbitrary `p_user_id` with no owner/admin check, letting any authenticated user probe whether another user applied to a job.

**Verdict**: NEEDS_CHANGES

## High-level view

The design is a straight table-API-to-RPC swap driven by a schema-cache bug, not a feature change. The behavioral contract that matters is that each RPC reproduces the row shape, ordering, and access rules the providers and UI previously relied on. Read shapes are preserved: setof-returning functions return the full row (`SELECT *`), casts on the Dart side (`List<Map>.from`, `int?`/`num`, single-row `.first`) match the declared return types, and the client-side status filter plus per-row `jobs`/`users` enrichment sub-maps are intact.

Security is now enforced in function bodies rather than by RLS. Admin-only reads/writes call `is_admin()`, owner-scoped functions compare `auth.uid()::text` to `user_id::text`, and the public-facing reads (`get_active_jobs`, `get_job_by_id`, `get_banners`) restrict to active/visible rows for non-admins — with one gap: `has_applied_to_job` trusts a caller-supplied user id.

The write path is where the RPC rewrite diverges from the old table writes. `create_job`/`create_banner` correctly move `created_by`/`status`/timestamps server-side, and `apply_to_job` uses a real INSERT so the `enforce_job_slots` trigger still fires. But the partial-update functions use `COALESCE` for text fields, which silently drops the ability to null out a column — a real difference from the previous `.update({...data})` behavior that the edit forms depend on.

1. **COALESCE blocks clearing text columns on edit** — `update_job` (`category`, `cover_image_url`, `title`, `description`) and `update_banner` (`title`, `image_url`, `link_type`, `link_page`) use `COALESCE(p_data->>'key', existing)`, so an explicit `null` from the edit form preserves the old value instead of clearing it. ### Partial-update semantics: COALESCE swallows explicit nulls

The edit forms build a full data map every time and send `null` for fields that should be cleared. `manage_banners_screen.dart` sends `link_campaign_id: null` and `link_page: null` whenever the link type isn't campaign/page; `post_job_screen.dart` sends `category: null` and `cover_image_url: null` when those inputs are blank. Under the old `.update({...data})` PostgREST write, those nulls were written through, clearing the columns.

The new functions split behavior by column. `deadline` and `max_slots` use `CASE WHEN p_data ? 'key' THEN (p_data->>'key')::type ELSE existing END`, so a present-but-null key resolves to `(null)::type` = NULL and the column clears correctly. But the text columns use `COALESCE(p_data->>'key', existing)`:

```sql
category = COALESCE(p_data->>'category', category),
cover_image_url = COALESCE(p_data->>'cover_image_url', cover_image_url),
...
link_page = COALESCE(p_data->>'link_page', link_page),
```

`p_data->>'category'` on a JSON null yields SQL NULL, so COALESCE falls back to the existing value. Net effect: an admin who clears a job's category or a banner's page link, then saves, sees the old value persist. `update_banner` is internally inconsistent here — `link_campaign_id` uses the `?`-key CASE form and *does* clear, while the sibling `link_page` uses COALESCE and does not, so flipping a banner from page to campaign leaves a stale `link_page`.

The plan (FEAT-001 step 5) prescribed the COALESCE shape, so this matches the spec — but it's still a real regression from the pre-change edit behavior and worth surfacing before it ships. The fix is to use the `?`-key CASE form for every column the forms are allowed to null.

### Access control moved from RLS into function bodies

With `SECURITY DEFINER` the functions run as the definer and RLS no longer applies, so each function re-implements the gate. Admin-only reads and every write (`get_jobs`, `get_submitted_applications`, `get_job_applicant_count`, `get_all_banners`, all create/update/delete, `get_application_core`, `update_application_status`) raise unless `is_admin()`; owner-scoped functions (`get_job_applications`, `submit_job_task`) compare `auth.uid()::text` to `user_id::text`; the public reads restrict to `status='active'`, non-active-behind-`is_admin()`, and `is_visible = true` respectively.

The gap is `has_applied_to_job(p_job_id uuid, p_user_id text)`, which runs an `EXISTS` against `job_applications` for the supplied `p_user_id` with no check that it equals `auth.uid()` or that the caller is admin. The provider passes the current user's own id, so normal use is fine, but the function itself lets any authenticated caller test arbitrary `(job_id, user_id)` pairs — an application-membership oracle. Deriving the id from `auth.uid()` inside the function, or gating non-self lookups behind `is_admin()`, closes it without changing the caller.

### Read-shape and enrichment parity

`apply_to_job` performs a real `INSERT INTO public.job_applications (...)`, so the `enforce_job_slots` BEFORE INSERT trigger still runs and the "no slots remaining" path is preserved. `create_job`/`create_banner` set `created_by = auth.uid()`, status/visibility defaults, and timestamps server-side, and the Dart writers stopped sending those fields — closing a client-supplied `created_by` spoofing vector that the old `.insert({..., 'created_by': user.id})` left open.

The status filter that was a server predicate on `myJobApplicationsProvider` is now applied client-side (`rows.where((r) => r['status'] == statusFilter)`); this yields the same set because `get_job_applications` returns all of the user's rows ordered by `applied_at DESC`. `SELECT *` in the setof functions preserves the full row, so the `{...row, 'jobs': ...}` / `{...row, 'users': ..., 'jobs': ...}` enrichment sub-maps the screens read still carry every depended-on column. The scalar returns are handled with `(response as int?) ?? (response as num).toInt()`, which is defensive against PostgREST returning the integer as a JSON num rather than an int.

### Approve/reject path left intact

`approveJobSubmission` and `rejectJobSubmission` now fetch the application's ids via `get_application_core` and the job title via `get_job_by_id` instead of table selects, then call `update_application_status`. The `credit_wallet` RPC call and both `.from('notifications').insert(...)` calls are byte-for-byte unchanged, and `update_application_status` sets `reviewed_at`/`reviewed_by` server-side as the old update did. `get_application_core` is admin-gated, so a non-admin invoking approve/reject fails at the first call rather than partway through — no half-applied wallet credit.
