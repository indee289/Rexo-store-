# Fix null-clearing, membership oracle, and link-column inconsistency in jobs/banners RPCs (v2)

The v1 pass flagged three defects in `supabase/jobs_banners_rpc.sql` and returned NEEDS_CHANGES. Since then only that SQL file changed — the two Dart providers and `error_utils.dart` are byte-for-byte identical to v1, so all RPC names, parameters, and call sites are unchanged. This pass confirms each fix against the actual edit-form payloads and re-checks the invariants that were clean in v1. All three issues are resolved and no regression was introduced.

Watch for: nothing blocking. The CASE-vs-COALESCE split now tracks each column's nullability — CASE for the nullable columns the forms can blank, COALESCE only on NOT NULL columns the forms always send.

**Verdict**: APPROVED

## High-level view

Issue 1 (COALESCE swallowed explicit nulls on edit) is fixed by switching the nullable text columns to the present-key CASE form. `update_job` now clears `category` and `cover_image_url` when the form sends them as null, and keeps COALESCE on `title`/`description`/`status`; `update_banner` uses CASE for `title` and keeps COALESCE on `image_url`/`link_type`. This matches what the forms send: `post_job_screen.dart` always emits `category` and `cover_image_url` keys (null when blank) and non-empty `title`/`description`; `manage_banners_screen.dart` always emits `title` (null when blank) and always sends `image_url`/`link_type`. No NOT NULL column can be nulled through either path.

Issue 2 (application-membership oracle) is fixed by converting `has_applied_to_job` to plpgsql and gating non-self, non-admin lookups with `IF auth.uid()::text <> p_user_id AND NOT public.is_admin() THEN RAISE EXCEPTION`. Return type and parameters are unchanged, and the Dart caller passes the user's own id, so the self path still returns the boolean.

Issue 3 (link_page vs link_campaign_id asymmetry) is fixed by giving `link_page` the same present-key CASE form as `link_campaign_id`. Since the banner form always sends both keys (null unless the matching link type is selected), switching a banner between page and campaign link types now clears the stale sibling column.

The v1-clean invariants still hold: zero `.from('jobs'|'job_applications'|'banners')` in `lib/`; 20 functions, each SECURITY DEFINER + `SET search_path = public` + a matching GRANT EXECUTE TO authenticated; `public.is_admin()` reused, never redefined; the file still ends with `NOTIFY pgrst, 'reload schema';`; `supabase_service.dart`, the `.from('users')`/`.from('notifications')` calls, and the `credit_wallet` RPC are untouched; `error_utils.dart` carries no DEBUG passthrough.

### Issue 1 — null-clearing on edit, verified against form payloads

`post_job_screen.dart` builds its map unconditionally with `category: <trim or null>` and `cover_image_url: <value or null>`, and `title`/`description` as trimmed (non-empty per form validation). It never sends a `status` key. `update_job` now reads:

```sql
category = CASE WHEN p_data ? 'category' THEN p_data->>'category' ELSE category END,
cover_image_url = CASE WHEN p_data ? 'cover_image_url' THEN p_data->>'cover_image_url' ELSE cover_image_url END,
title = COALESCE(p_data->>'title', title),
description = COALESCE(p_data->>'description', description),
status = COALESCE(p_data->>'status', status),
```

Because the form always sends `category` and `cover_image_url` keys, the CASE form resolves to the JSON null → SQL NULL and the column clears — the v1 regression is gone. `title`/`description` are NOT NULL and always arrive as non-empty text, so COALESCE never falls back and never writes NULL. `status` is NOT NULL and never sent, so COALESCE preserves the existing value. No NOT NULL column can be nulled.

`manage_banners_screen.dart` always sends `title` (null when blank), `image_url`, `link_type`, `link_campaign_id`, `link_page`, and `is_visible`. `update_banner` now uses CASE for `title` (nullable, clears correctly) and keeps COALESCE on `image_url` (NOT NULL, always sent) and `link_type` (CHECK-constrained, always sent). The reorder path that sends only `{'sort_order': i}` still behaves: the absent `title`/`link_page`/`link_campaign_id` keys leave those columns untouched via CASE, and the absent `image_url`/`link_type` keys resolve to NULL → COALESCE preserves.

### Issue 2 — membership oracle closed

`has_applied_to_job` is now plpgsql with the guard before the EXISTS:

```sql
IF auth.uid()::text <> p_user_id AND NOT public.is_admin() THEN
  RAISE EXCEPTION 'Unauthorized';
END IF;
```

An authenticated caller can only probe their own `(job_id, user_id)` state; admins may probe any. The Dart caller (`params: {'p_job_id': jobId, 'p_user_id': user.id}`) passes its own id, so `auth.uid()::text = p_user_id` and the self path proceeds to return the boolean. Return type (`boolean`) and parameter list (`p_job_id uuid, p_user_id text`) are unchanged, so the call site needs no edit. This mirrors the same guard already present on `get_job_applications`.

### Issue 3 — link column clears symmetric

```sql
link_campaign_id = CASE WHEN p_data ? 'link_campaign_id' THEN (p_data->>'link_campaign_id')::uuid ELSE link_campaign_id END,
link_page        = CASE WHEN p_data ? 'link_page'        THEN p_data->>'link_page'                ELSE link_page END,
```

The form sends `link_campaign_id: _linkType == 'campaign' ? id : null` and `link_page: _linkType == 'page' ? text : null`. With both on the present-key CASE form, switching a banner from a page link to a campaign link sends `link_page: null` (present key) which now clears it, and vice versa. The v1 asymmetry where `link_page` used COALESCE and retained stale values is gone.
