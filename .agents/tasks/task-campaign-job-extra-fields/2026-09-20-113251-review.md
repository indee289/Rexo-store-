# Optional rules, demo asset, and multi-platform for campaigns and jobs (v1)

Campaigns and jobs (both rows in `public.campaigns`, jobs tagged `payout_model='job'`) gain three new inputs on their create/edit forms and their detail screens: a free-text description/rules block, an optional per-type demo asset (image/video/pdf/link/text), and multi-select platforms replacing the old single-platform dropdown. The three new columns (`rules`, `demo_asset_type`, `demo_asset_url`) ship as an idempotent hand-run SQL migration and are written only as insert/update VALUES and read back off `SELECT *` result maps — the hard PostgREST constraint that a newly-added column must never be named in a `.select()` projection or a query filter is respected everywhere. A single shared `DemoAssetField` picker and `DemoAssetView` renderer keep the campaign and job paths behaviorally identical. Optional sections are individually gated on non-empty data on both detail screens, and no mock/static data was introduced.

**Watch for:** campaign description was made a **required** validated field (confirmed) though the user framed the three additions as optional — verify this is intended. Multi-platform values render un-split (`"Instagram,Facebook"` with no spaces) in the campaign detail's brand subtitle and "Content Type" row (confirmed) — the new pills split correctly, but those two legacy text spots do not.

**Verdict**: NEEDS_CHANGES

## High-level view

Persistence is correct and symmetric across both paths. The campaign form writes `description` and comma-joined `platform` unconditionally and adds `rules`/`demo_asset_type`/`demo_asset_url` only when populated (nulling them on edit when cleared); the job form routes the same four fields through `jobsProvider.createJob` (plain insert values) and `updateJob` (containsKey-guarded pass-through). Read-back relies on the `...row` spread in `_mapCampaignToJob` and the arg-less `SELECT *` in the campaign providers, so the new columns arrive by key without ever being named. The data-model constraints hold.

The demo-asset value semantics are consistent end to end: image/video/pdf resolve to an R2 URL, link to the pasted URL, text to the raw body, and a type is only ever persisted when it has an accompanying value (`hasDemoAsset` gate on write, `type && url` gate on read). Selecting a type but not supplying a value writes nothing, and both detail screens hide the section unless both fields are present.

The one requirement tension is the description field: the user described all three new inputs as optional, but the campaign form validates description as required. The job form leaves its pre-existing description behavior untouched, so the two paths now diverge on whether a description is mandatory.

The multi-platform round-trip (join on write, split+filter on prefill, split into pills on display) is sound, but two un-migrated text spots on the campaign detail screen still print the raw comma-joined string.

<summary>Details</summary>

### The write/read contract holds

The PostgREST constraint is the load-bearing part of this change. Across the touched files, the four fields appear only inside `insert({...})` / `update` maps (`jobs_provider.dart`) and as `data[...]` assignments in the two forms; a grep for the column names inside any `.select(...)` projection returns nothing, and the only `payout_model` references left are explanatory comments, not `.eq/.neq/.filter` calls. Job read-back rides the `...row` spread in `_mapCampaignToJob`; campaign read-back rides the arg-less `SELECT *` (and `SELECT '*, users!brand_id(...)'`, which names only the join, not the new columns). Edit prefill therefore gets the raw column values by key on both paths.

### Demo asset value semantics

`_selectType` clears the transient state that doesn't belong to the newly-chosen type, so switching types can't carry a stale URL or body into the persisted value. Both forms gate the write on `hasDemoAsset` (`type != none && value non-empty`), so a half-filled picker (type chosen, nothing uploaded/entered yet) persists nothing rather than a dangling type, and both detail screens further require `demoType && demoUrl` before rendering. The video/pdf/link launches go through `url_launcher` `externalApplication` guarded by `Uri.tryParse`, and a malformed URL silently no-ops.

### Description made required

The campaign form's new description field carries a validator that rejects an empty value (`'Campaign description is required'`), which contradicts the user's framing of the three additions as optional and diverges from the job form, whose description remains as it was. If a required description is a deliberate product decision it should be applied to the job form too; otherwise the validator should be removed so description is genuinely optional.

### Multi-platform round-trip and the un-split display

Write joins `_selectedPlatforms` with `,`; prefill splits on `,`, trims, filters to known platforms case-insensitively, dedupes, and falls back to the existing single selection when parsing yields nothing; the chip UI keeps at least one platform selected. That round-trip is clean. The gap is on the campaign detail screen: the new pills row correctly splits into one `_Pill` per platform, but the brand subtitle (`subtitleParts`) and the "Content Type" detail row still interpolate the raw `platform` string, so a two-platform campaign shows `"Instagram,Facebook"` with no separator in those two spots. The job detail screen has no equivalent raw-string spot. Join the split list for those two campaign-detail strings.

### Dark-mode safety

Every new surface branches on `Theme...brightness`: the demo-asset selector, video upload area, both detail Rules cards, `DemoAssetView`'s image/link/text cards, and the job `_PlatformPill` all pick `dark*` vs light tokens (`darkCard`, `darkSurfaceAlt`, `darkBorder`, `darkText*`). The campaign form's platform chips use `theme.colorScheme`/`dividerColor` rather than the app's `dark*` tokens, which is a slightly different styling path than the rest of the file but still theme-driven, not hard-coded.

### Test coverage

Not tested: there is no automated suite for this UI and the sandbox can't run `flutter analyze`/`build`/`test` or reach Supabase, so verification is static only. The write→read→prefill loop for all three fields on both paths, the demo-asset upload to R2, and the `url_launcher` open paths are unexercised and should be smoke-tested manually against a DB that has run the migration.
