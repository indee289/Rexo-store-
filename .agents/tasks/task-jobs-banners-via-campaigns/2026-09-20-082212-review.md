# Job/campaign application isolation and re-added slot enforcement (v2)

The v1 review flagged six issues on the piggyback design that serves jobs as `campaigns` rows (`is_job=true`), job applications as rows in the shared `applications` table, and banners as a JSON array in `platform_settings`. The fix pass (a4160fb) added an embedded `is_job` filter to both campaign application-list providers, a `jobRow == null` skip in My Jobs, a server-side `enforce_job_slots` trigger on `applications`, and an `is_job=true` guard on `deleteJob`; the two remaining issues (duplicate-apply UX, non-atomic banner writes) were accepted with documented rationale.

Watch for: nothing blocking. All four code fixes are present in the working tree and correctly reasoned, and no new regression was introduced — the leak filters treat null/absent embedded campaigns as not-a-job so real campaign applications are never dropped (confirmed), and the slot trigger is scoped to `is_job=true` campaigns so it cannot fire on real campaign applications (confirmed). The two accepted limitations are reasonable for the stated single-admin / UI-gated usage.

**Verdict**: APPROVED

## High-level view

The two directional leaks are closed by the same discriminator: the embedded campaign's `is_job` flag. `myApplicationsProvider` and `appliedCampaignsProvider` now request `is_job` in their embedded `campaigns(...)` projection and drop rows where it is `true`, while a null or absent embedded campaign falls through as not-a-job so a real application whose join happens to be empty is still kept. `myJobApplicationsProvider` runs the mirror logic: it re-fetches each row's campaign with `.eq('is_job', true)` and now `continue`s when that fetch returns null, so real campaign applications no longer render as phantom "Untitled Job"/₹0 cards. The two paths use disjoint insert statuses (`applied` for jobs, `pending` for campaigns), which reinforces the separation but is not what the filters rely on.

Server-side slot enforcement is restored as a `BEFORE INSERT` trigger on `applications` that looks up the target campaign and enforces only when `is_job IS TRUE AND total_slots > 0`, counting `applied/submitted/approved` rows — matching the Dart `jobSlotCountProvider`. Real campaign applications (`is_job=false`/null) and unlimited jobs (`total_slots` 0/null) are never blocked. It is idempotent (`CREATE OR REPLACE FUNCTION` + `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER`) and placed in section 7, before the final `NOTIFY pgrst` in section 8.

`deleteJob` gained `.eq('is_job', true)`, so a stray real-campaign id reaching the jobs delete path is a no-op rather than a cascade-deleting hard delete. Duplicate-apply is left to `UNIQUE(campaign_id, creator_id)` plus the `hasAppliedToJobProvider` UI gate and the existing catch that converts the throw to a returned `false`; the misleading `applyToJob` comment was corrected. Non-atomic banner read-modify-write is accepted as a single-admin limitation.

### Both application leaks closed via the embedded is_job flag

The v1 leaks came from three providers filtering the shared `applications` table by `creator_id` alone. The fix uses the embedded campaign's `is_job` as the discriminator in both directions, and the null-handling is the part worth checking closely because getting it wrong would drop real applications.

On the campaigns side, `myApplicationsProvider` now selects `campaigns(id, title, status, cover_image_url, is_job)` and skips a row only when `campaign != null && campaign['is_job'] == true`. A row with a null or absent embedded campaign is kept, so a real campaign application whose join is empty (deleted campaign, RLS edge) is never dropped. `appliedCampaignsProvider` already skipped null-campaign rows for its flatten step and now additionally `continue`s on `campaign['is_job'] == true`; its `campaigns(*)` projection already returns `is_job`. Correctness rests on `is_job`, not on the disjoint insert statuses (`pending` for campaigns, `applied` for jobs).

On the jobs side, `myJobApplicationsProvider` re-fetches each application's campaign with `.eq('is_job', true).maybeSingle()`; a real campaign application returns null there, and the added `if (jobRow == null) continue;` drops it before the enriched map is built. The stale `'jobs': jobRow ?? {}` fallback was replaced with `'jobs': jobRow` (now guaranteed non-null), eliminating the empty-card path entirely. This mirrors `adminJobSubmissionsProvider`, which additionally filters `status='submitted'` (a status real campaign applications never hold).

### Slot enforcement restored and correctly scoped

The trigger reads the target campaign once and gates on `v_is_job IS TRUE AND v_total_slots IS NOT NULL AND v_total_slots > 0`, so it is inert for real campaign applications and for unlimited jobs (the `0`/null convention). When active it counts `applied/submitted/approved` rows for the same `campaign_id` and raises `'This job has no slots remaining.'` at capacity.

```
INSERT INTO applications (campaign_id = X)
        │
        ▼  BEFORE INSERT enforce_job_slots
   campaigns[X].is_job = true AND total_slots > 0 ?
        ├── no  → RETURN NEW            (real campaign app, or unlimited job)
        └── yes → count applied/submitted/approved for X
                     ≥ total_slots ? RAISE : RETURN NEW
```

The counted-status set matches `jobSlotCountProvider` (line 98), so the server cap and the client's `isFull` display agree, and `SECURITY DEFINER` lets the count see all applicant rows regardless of the caller's RLS view — required for the cap to be accurate. Idempotency: `CREATE OR REPLACE FUNCTION`, then `DROP TRIGGER IF EXISTS enforce_job_slots ON public.applications`, then `CREATE TRIGGER`, all ahead of the section-8 `NOTIFY pgrst, 'reload schema'` that remains the file's final statement. The `applyToJob` doc comment was rewritten to point at this trigger on `applications` rather than the dead `job_applications` trigger, so the false claim from v1 is gone.

One residual note, not a regression from this pass: because enforcement is a subquery count rather than a locking reservation, two concurrent inserts at exactly `total_slots - 1` used can both pass the check under low isolation. This narrows but does not fully eliminate the race the v1 review described; for the expected apply volume it is a negligible risk, and no change is warranted.

### deleteJob guard

`deleteJob` now chains `.eq('id', jobId).eq('is_job', true)`, so a non-job campaign id reaching this path deletes nothing instead of hard-deleting a real campaign and cascade-removing its applications. Callers only ever pass job ids, so this is defense-in-depth rather than a fix for a live bug.

### Accepted limitations

Duplicate-apply relies on `UNIQUE(campaign_id, creator_id)` plus the `hasAppliedToJobProvider` button gate; a racing second insert throws and the existing catch returns `false` with an error state rather than a tailored message. Banner mutations remain a whole-array read-modify-write on the single `home_banners` row, so simultaneous admin edits can overwrite each other. Both are documented as accepted for the current single-admin, UI-gated usage; neither blocks.

### Regression check

The v1 "still-good" properties hold under the fix pass. Home and Campaigns list queries still carry `.eq('is_job', false)`; the campaign/wallet/notification paths (`applyToCampaign`, `credit_wallet` RPC, the `job_approved`/`job_rejected` notification inserts) are untouched by a4160fb; the migration still adds no `public.jobs/job_applications/banners` relation and its CHECK relaxations remain supersets; banners still return `[]` (genuine empty state, no mock data) on a missing/unparseable value. The two specific regressions the brief asked to rule out — real campaign apps dropped by the new filters, and the slot trigger misfiring on campaigns — are both excluded by the null-safe filter logic and the `is_job` trigger guard respectively.
