# Jobs and Banners served through the already-cached campaigns / platform_settings tables (v1)

Jobs, job applications, and banners have been re-plumbed onto tables PostgREST already serves, to sidestep the persistent PGRST205 on the standalone `jobs`/`job_applications`/`banners` relations. Jobs become `campaigns` rows tagged `is_job = true`; job applications become `applications` rows keyed by the job's `campaign_id`; banners become a single JSON array stored under `platform_settings.key = 'home_banners'`. A guarded, idempotent migration adds the marker column and job-submission columns, relaxes two CHECK constraints, adds an admin DELETE policy, and best-effort-copies any surviving legacy rows before `NOTIFY pgrst`. The Dart providers keep every public name/signature so the screens are untouched.

Watch for: the `applications` table is now shared by real campaign applications and job applications with no discriminator column, so job rows leak into the creator's campaign-application lists and campaign rows leak into the My Jobs list under the All/Approved/Rejected filters (confirmed). Server-side slot enforcement is gone — the old trigger was bound to the now-unused `job_applications` table and no equivalent was added on `applications`, yet `applyToJob` still claims it is enforced (confirmed). Column mapping, banner CRUD, and isolation of the Home/Campaigns lists are otherwise sound.

**Verdict**: NEEDS_CHANGES

## High-level view

The piggyback approach attacks the root cause directly: `ALTER TABLE ... ADD COLUMN` on an already-cached relation never leaves the schema cache, so PGRST205 cannot recur. The Dart⇄SQL column mapping (`per_creator_payout`↔`payment_amount`, `total_slots`↔`max_slots` with `0`=unlimited) is symmetric on read and write, and every key the job screens read is present in the returned maps.

The central weakness is that jobs and campaigns now share the `applications` table with no per-row discriminator. Providers that filter only by `creator_id` (`myApplicationsProvider`, `appliedCampaignsProvider`, `myJobApplicationsProvider`) return both kinds of rows. Job applications surface in the creator's campaign screens, and campaign applications surface as empty "Untitled Job" cards in My Jobs under status filters that overlap (`approved`/`rejected`/`all`). The admin submission list is the one query that is safe here, because it filters on `status = 'submitted'` (a job-only status) and re-checks `is_job` per row.

Slot enforcement regressed silently. The BEFORE INSERT trigger that capped applicants lived on `job_applications`; the migration adds no replacement on `applications`, so the only remaining guard is the client hiding the apply bar. The `applyToJob` comment asserting server-side enforcement is now false.

The Home and Campaigns lists exclude `is_job = true` rows, the migration's CHECK relaxations are proper supersets of the prior allowed values, and campaign/wallet/notification behavior for real campaigns is untouched. One residual gap: banner CRUD does a non-atomic read-modify-write of the whole array, so concurrent admin edits can clobber each other.

### Shared applications table with no discriminator

Job applications and campaign applications now coexist in `applications`, distinguished only by whether their `campaign_id` points at an `is_job = true` row. Nothing on the application row itself says which kind it is, so any provider that queries by `creator_id` alone returns both.

```
applications (creator_id = me)
├── campaign_id → campaigns(is_job = false)   ← real campaign application
└── campaign_id → campaigns(is_job = true)    ← job application
```

`myApplicationsProvider` (`select('*, campaigns(id, title, status, cover_image_url)')`) and `appliedCampaignsProvider` (`select('status, created_at, campaigns(*, ...)')`) both embed the campaign without an `is_job` filter, so a job application's parent job row comes back non-null and flows straight into the creator's My Campaigns list and the Campaigns tab. `appliedCampaignsProvider` only skips rows whose embedded campaign is null, which never happens for a job row. Both need to exclude job rows — filtering the embedded resource on `is_job = false`, or better, adding a stored discriminator so the filter doesn't depend on an embedded join.

The reverse leak is `myJobApplicationsProvider`: it selects `applications` by `creator_id` with an optional `status` filter, then enriches each row by fetching `campaigns ... .eq('is_job', true).maybeSingle()`. For a real campaign application that fetch returns null, so `jobRow` falls back to `{}` and the row is still appended. The My Jobs card then renders `'Untitled Job'`, category null, ₹0. Because the status tabs are `all / applied / submitted / approved / rejected` and campaign applications carry `approved`/`rejected` (and appear under `all`), those three tabs show phantom entries. The fix mirrors what `adminJobSubmissionsProvider` already does correctly — `if (jobRow == null) continue;` — dropping non-job rows before appending.

`adminJobSubmissionsProvider` is the model to copy: it filters `status = 'submitted'` (a status real campaign applications never hold) and additionally skips any row whose campaign is not `is_job = true`. That double guard keeps the admin review queue clean and is worth preserving. `campaignApplicantsProvider` is keyed by a specific `campaign_id` and is only ever invoked for real campaigns, so it does not mix in job applicants.

### Slot enforcement no longer exists server-side

The prior design enforced slot limits with a BEFORE INSERT trigger, `enforce_job_slots`, on `public.job_applications`, which counted existing rows and raised when full. Jobs now insert into `applications`, and `JOBS_VIA_CAMPAIGNS.sql` adds no trigger there, so the old trigger is dead code on an unused table.

```
apply → applications INSERT   (no BEFORE INSERT slot check)
job_detail_screen: isFull = maxSlots != null && slotFilled >= maxSlots  ← client only
```

The only remaining guard is the client hiding `_ApplyBar` when `isFull`. `slotFilled` comes from `jobSlotCountProvider` counting `applied/submitted/approved` rows, so the count is correct for display, but two users applying concurrently — or any direct write — can exceed `max_slots`. `applyToJob`'s comment ("Enforced server-side by the slot-check trigger") is now inaccurate and should either be made true with a trigger on `applications` (scoped to job campaigns) or corrected.

### Duplicate-apply hits a raw uniqueness error

The column mapping and screen-key coverage line up on both directions (`_mapCampaignToJob` and the `createJob`/`updateJob` inverse), including the `0`=unlimited convention and the nested `jobs`/`users` shapes the admin and My Jobs cards read. One edge lacks a guard: `applications` has `UNIQUE(campaign_id, creator_id)`, so a second `applyToJob` for the same job throws a raw uniqueness error rather than a handled message. `hasAppliedToJobProvider` uses `maybeSingle()` (safe under the unique constraint) and should gate the button, but the insert path has no explicit conflict handling.

### Banners write is a non-atomic read-modify-write

Banners are one JSON string under `platform_settings.value` for `key = 'home_banners'`, and CRUD keys off a generated `id` (`microsecondsSinceEpoch`). `_readBanners` returns `[]` on a missing row, null/empty value, non-list JSON, or parse error — a genuine empty state with no mock data. The gap is that every mutation reads the whole array, edits it in memory, and upserts it back; two concurrent admin edits therefore clobber each other. Acceptable for a single-admin banner workflow, but a real concern if banner administration ever runs concurrently.

### Migration idempotency and safety

The migration adds `is_job` with `IF NOT EXISTS`, adds the seven submission columns the same way, and drops-then-recreates both CHECK constraints as strict supersets of the originals (`campaigns`: adds `closed`; `applications`: adds `applied`,`submitted`), so no previously valid value is rejected. The admin DELETE policy is `DROP POLICY IF EXISTS` then `CREATE`. The three data-copy blocks are guarded by `to_regclass(...)` and use `ON CONFLICT (id) DO NOTHING` (jobs/apps) or `ON CONFLICT (key) DO UPDATE` (banners), preserving ids so relationships line up; the job-application copy additionally requires the parent campaign to exist. No `public.jobs/job_applications/banners` relation is created, and the file ends with `NOTIFY pgrst, 'reload schema'`.

### Unrelated change bundled in

`error_utils.dart` drops the temporary `DBG3` passthrough that short-circuited `sanitize()` and returned the raw error string, restoring normal error categorization. This is a cleanup unrelated to the piggyback mechanism but is the correct thing to remove.
