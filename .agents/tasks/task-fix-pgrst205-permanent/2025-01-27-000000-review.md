# Permanent PGRST205 fix via table/schema GRANTs for jobs, job_applications, banners (v1)

A single idempotent SQL script (`supabase/FIX_PGRST205_permanent.sql`) that the user runs once in the Supabase SQL Editor to clear the persistent `PGRST205 "Could not find the table 'public.jobs' in the schema cache"` error on the Jobs and Banners screens. The change diagnoses and then repairs the actual root cause: the three tables were created (in `jobs_banners_LIKE_CAMPAIGNS.sql`) without the table-level, schema-usage, and sequence GRANTs to `anon`/`authenticated`/`service_role` that PostgREST needs to include a relation in its schema cache — the working `campaigns` table inherited those privileges from Supabase's platform default privileges, the newer tables did not. The script also normalizes table ownership to `postgres`, sets `ALTER DEFAULT PRIVILEGES` so future tables inherit the grants, re-asserts the twelve campaigns-style RLS policies defensively (drop-if-exists then create, no table drop), and reloads PostgREST. It deliberately does not drop or recreate the tables, so existing rows survive.

The root cause matches the observed evidence: campaigns has no explicit GRANT in `schema.sql` yet works, because a table PostgREST's API role has zero privileges on is excluded from the schema cache and surfaces as PGRST205 — which survives both `NOTIFY` and a project restart because neither adds privileges. The RLS policy bodies are copied verbatim from the source file. The one thing a reviewer should weigh is the deliberately broad `GRANT ALL ... TO anon`: consistent with the Supabase default-privilege posture the working tables already carry, but it grants the unauthenticated role write/TRUNCATE privileges that RLS does not fully constrain.

**Watch for:** `GRANT ALL ... TO anon` includes INSERT/UPDATE/DELETE/TRUNCATE to the unauthenticated role; RLS covers row DML but not `TRUNCATE`, so anon can truncate these tables through a direct DB role even though it matches the platform default posture (confirmed). `GRANT ALL ON ALL SEQUENCES IN SCHEMA public` is a schema-wide no-op for these three tables since all PKs are `gen_random_uuid()` with no sequences (confirmed).

**Verdict**: APPROVED

## High-level view

The fix targets the correct root cause. PostgREST builds its schema cache as the API roles (`anon`, `authenticated`), and a relation those roles hold no privilege on is omitted from the cache and reported as PGRST205 — which is exactly why a table rebuild, `NOTIFY`, and a full project restart never resolved it: none of them grant privileges. `campaigns` works because objects created during Supabase provisioning inherited default privileges the later ad-hoc `CREATE TABLE`s did not. Section B closes that gap with schema `USAGE`, table `GRANT ALL`, sequence grants, and `ALTER DEFAULT PRIVILEGES` for future objects, plus an ownership normalization to `postgres`.

The script is safe to re-run: it never drops the tables, sequence and default-privilege grants are naturally idempotent, and the RLS re-assertion uses `DROP POLICY IF EXISTS` before each `CREATE POLICY`. Existing job and banner rows are preserved — a meaningful improvement over the earlier rebuild script that dropped and recreated the tables.

The security posture is inherited from the working baseline rather than tightened. `GRANT ALL` to `anon` matches what `campaigns` already carries, so it is internally consistent, but it hands the unauthenticated role write and `TRUNCATE` privileges. RLS gates row-level reads/writes but does not apply to `TRUNCATE`, so this is the one place where "match campaigns exactly" and "least privilege" diverge.

The twelve re-asserted policies are byte-for-byte identical to the bodies in `jobs_banners_LIKE_CAMPAIGNS.sql`, so no existing access is narrowed or broadened. The runbook is sequenced well for a stressed non-expert: diagnostics first, one-shot run, wait, refresh, then a Dashboard exposed-schema / restart fallback if it still fails.

### Why the previous attempts could not have worked

PostgREST introspects the database as its configured API roles and only caches relations those roles have at least one privilege on. A table with no grant to `anon`/`authenticated` is invisible to the cache and every request for it returns PGRST205 with "not found in the schema cache" — the same message as a genuinely missing table, which is what sent the earlier debugging down the rebuild path. Because the missing element is a *privilege*, not a *definition*, rebuilding the table, issuing `NOTIFY pgrst, 'reload schema'`, and restarting the project all reload the same privilege-less state and the error persists. `schema.sql` contains no `GRANT` statements at all yet `campaigns` is queryable, which confirms the working table's access comes from Supabase's platform-level default privileges applied at provisioning time, not from anything in the repo — and that the later `CREATE TABLE`s in `jobs_banners_LIKE_CAMPAIGNS.sql` fell outside that inheritance. Section B's combination of `GRANT USAGE ON SCHEMA public`, per-table `GRANT ALL`, and `ALTER DEFAULT PRIVILEGES` is the correct and complete remedy for that failure mode.

### Grant breadth vs. the RLS trust boundary

```
anon ──(GRANT ALL)──► jobs / job_applications / banners
                         │
              RLS row policies  ── gate SELECT/INSERT/UPDATE/DELETE per row
                         │
              TRUNCATE ──────────► NOT covered by RLS
```

RLS is enabled on all three tables and the policies restrict row-level reads and writes, so the practical exposure from `GRANT ALL` to `anon` is limited for ordinary DML. The gap is `TRUNCATE`, which RLS does not evaluate: a client authenticating as the raw `anon` DB role could truncate these tables. This is the same posture the working `campaigns` table already carries via default privileges, so the script is internally consistent and matches the stated goal of mirroring campaigns exactly — it is called out because the diff touches the trust boundary (grants to the unauthenticated role), not because it regresses relative to the baseline. A least-privilege alternative would grant `anon` only `SELECT` and reserve the broader grants for `authenticated` and `service_role`.

### RLS re-assertion fidelity

All twelve policies in Section C match the bodies in `jobs_banners_LIKE_CAMPAIGNS.sql` verbatim — the `status = 'active' OR created_by = auth.uid()` read predicate on jobs, the `auth.uid() = user_id` self-service predicates on applications, the `is_visible = TRUE` read predicate on banners, and the inline `EXISTS (SELECT 1 FROM users WHERE id = auth.uid() AND role = 'admin')` admin check throughout. Because each `CREATE POLICY` is preceded by `DROP POLICY IF EXISTS`, re-running does not stack duplicate policies and cannot silently narrow access.

### Idempotency and data safety

The script never touches table data — no `DROP TABLE` — which is the key contrast with `jobs_banners_LIKE_CAMPAIGNS.sql`, whose drop-and-recreate destroys existing job/banner rows. Grants, `ALTER DEFAULT PRIVILEGES`, ownership reassignment, and the guarded policy re-assertion are all repeatable, so re-running is non-destructive.

### Runbook fallback covers the other PGRST205 cause

The runbook's last-resort pointer to Dashboard → Settings → API "Exposed schemas" matters because a `public` schema missing from the API config produces the identical PGRST205 independent of grants — the one root cause this script's SQL cannot fix from the SQL Editor. Sequencing diagnostics (Section A) before the fix also gives the user a concrete campaigns-vs-broken-tables before/after to confirm the diagnosis.
