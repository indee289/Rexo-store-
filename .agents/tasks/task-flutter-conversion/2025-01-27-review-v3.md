# Flutter conversion — v3 final review

All 13 issues from v1 and v2 have been addressed across commits 1f40c0f and 4747e38. One new concern emerges on this pass: the `users` table RLS policies restrict SELECT to "own data" and "admin reads all," but multiple queries across campaigns, messages, and home screens join against `users` to fetch brand names, creator names, and avatars for *other* users. Those joins will return null data at runtime because the calling user isn't an admin and isn't the row owner.

Watch for: campaigns, messages, and creator listings will fail to display other users' names and avatars because users-table RLS blocks cross-user reads (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The single blocking gap is that the `users` table SELECT policy is too restrictive for an app that routinely needs to display other users' public identity (name, avatar, handle). Every PostgREST foreign-key join against `users` from campaigns, messages, or creator_profiles will silently return null for the joined fields, producing a broken UI for non-admin users.

## Users RLS prevents cross-user joins

The users table defines two SELECT policies:

```sql
CREATE POLICY "Users can read own data" ON users
    FOR SELECT USING (auth.uid() = id);

CREATE POLICY "Admins can read all users" ON users
    FOR SELECT USING (
        EXISTS (SELECT 1 FROM users WHERE id = auth.uid() AND role = 'admin')
    );
```

The app performs cross-user reads in at least four places:

```dart
// campaigns_provider.dart
.select('*, users!brand_id(id, name, avatar_url)')

// home_provider.dart (trending creators)
.select('*, users!inner(name, avatar_url, handle)')

// messages_provider.dart
.select('*, receiver:users!receiver_id(id, name, avatar_url)')
.select('*, sender:users!sender_id(id, name, avatar_url)')
```

In Supabase's PostgREST layer, foreign-key joins are executed as nested SELECTs under the same RLS context. When user A browses campaigns created by brand B, the inner `SELECT name, avatar_url FROM users WHERE id = B.id` is evaluated against A's RLS context. Neither policy matches (A isn't B, and A isn't admin), so the join returns null.

The result: campaign cards show no brand name/avatar, the messages screen shows no contact names, and the trending creators list is empty — all without any error being thrown.

The fix is straightforward: add a permissive SELECT policy that exposes the identity columns to any authenticated user. If there's concern about exposing sensitive fields (email, phone, account_status), create a view or restrict the policy with a column-level approach. But the current state is functionally broken for the app's primary use cases.
