# Kotlin-to-Flutter rewrite with Supabase backend

A complete rewrite of the Rexo influencer marketplace from Kotlin/Android to Flutter, replacing the previous Supabase client with supabase_flutter and rebuilding all screens as Riverpod-managed widgets. The app covers auth, campaigns, shop, wallet, messaging, and notifications with a new unified SQL schema (17 tables with RLS). The Flutter codebase follows a feature-first directory structure with GoRouter for navigation and a shared theme system.

Watch for: the `createUserProfile` call inserts a `full_name` column that doesn't exist in the schema (confirmed — will fail at runtime); the deposit-proofs upload calls `getPublicUrl` on a private bucket (confirmed — URLs will 403); withdrawals have no server-side balance enforcement (confirmed — RLS allows any insert); and the Supabase project URL is hardcoded as a default value in source, leaking the instance identifier to anyone who reads the repo.

**Verdict**: NEEDS_CHANGES

## High-level view

The schema is a clean-slate replacement — old tables dropped unconditionally, new tables created with RLS enabled on all 17, and a trigger auto-creates wallets on user insert. The policies are well-scoped per role but lack any server-side guard against withdrawals exceeding available balance; the only check is a client-side form validator.

State management uses Riverpod FutureProviders for reads and StateNotifiers for mutations. Every provider accesses `SupabaseService.currentUser` synchronously without null-guarding at the data layer, meaning a race between auth state change and provider refresh could produce null-pointer errors.

Registration calls `createUserProfile` with a `full_name` field that doesn't match the schema column `name`, so every signup will throw a Postgres error. The messages provider has the same mismatch in its join queries.

The financial flows — deposits, withdrawals, and shop checkout — all write directly to the database from the client. No edge functions validate amounts, check stock, or enforce idempotency. The checkout creates an order and order items in two separate inserts without a transaction, so a failure between them leaves an orphaned order row.

`AppConstants` has the production Supabase URL baked in as a `defaultValue`, meaning debug builds and anyone reading the repo can identify and hit the real instance directly.

There is zero test coverage. No unit tests, no widget tests, no integration tests across 48 Dart files.

<summary>Issues (9)</summary>

1. **`full_name` column mismatch** — `createUserProfile` inserts `full_name` but the schema column is `name`. Every registration will fail with a Postgres column-not-found error. Change the insert key to `name`.
2. **Messages provider references `full_name`** — The conversations query selects `users!receiver_id(id, full_name, avatar_url)` but the column is `name`. Same fix: use the correct column name.
3. **Private bucket public URL** — `deposit_screen.dart` calls `getPublicUrl` on the `deposit-proofs` bucket which is created with `public = FALSE`. Use `createSignedUrl` instead, or make the bucket public if proofs don't need protection.
4. **No server-side withdrawal balance check** — The RLS INSERT policy on `withdrawals` only verifies `auth.uid() = user_id`. Nothing prevents inserting a withdrawal exceeding `available_balance`. Add a Postgres check constraint or an edge function that validates balance before inserting.
5. **Checkout non-atomic writes** — `placeOrder` inserts the order row and then the order items in separate calls. If the items insert fails, an empty order persists. Wrap in an RPC/edge function with a transaction, or use Supabase's `rpc` for atomic multi-table inserts.
6. **Hardcoded Supabase URL in source** — `AppConstants.supabaseUrl` has the real project URL as a `defaultValue`. Remove the default or replace with a placeholder that clearly fails, forcing the build to supply the secret.
7. **Admin seed user with fake UUID** — The schema inserts an admin user with `00000000-0000-0000-0000-000000000001` which doesn't reference any `auth.users` row. The FK constraint `REFERENCES auth.users(id)` will reject this unless auth has a matching entry. Move to a post-auth migration script or documented manual step.
8. **No test coverage** — 48 Dart files and zero tests. At minimum, unit tests for providers and widget tests for critical flows (auth, checkout) should exist before shipping.
9. **`_authSubscription` never assigned** — `AuthNotifier` declares `_authSubscription` but the `listen` call in `_initialize` doesn't assign to it, so `dispose` cancels nothing and the stream subscription leaks.

## Schema-to-code column name mismatch

The SQL schema defines the users table with a `name TEXT NOT NULL` column. The Dart `SupabaseService.createUserProfile` method inserts:

```dart
await client.from('users').insert({
  'id': userId,
  'email': email,
  'full_name': fullName,  // ← column doesn't exist
  'role': role,
  'created_at': DateTime.now().toIso8601String(),
});
```

This will throw a Postgres error on every registration attempt. The messages provider compounds the problem by selecting `full_name` in its join:

```dart
.select('*, receiver:users!receiver_id(id, full_name, avatar_url)')
```

Both need to reference `name` to match the schema. The edit profile screen already uses `name` correctly, indicating an inconsistency between features rather than a design disagreement about the column name.

## Wallet withdrawal without server-side guard

`WalletActionsNotifier.submitWithdrawal` inserts directly into the `withdrawals` table. The RLS policy:

```sql
CREATE POLICY "Users can create withdrawals" ON withdrawals
    FOR INSERT WITH CHECK (auth.uid() = user_id);
```

A crafted request can insert any amount. The `wallets` table has no trigger or constraint that deducts balance on withdrawal insert — balance management is entirely manual/admin. The absence of even a `BEFORE INSERT` trigger means the data layer permits obviously invalid states (e.g., withdrawing 10x balance).

A trigger that verifies `amount <= (SELECT available_balance FROM wallets WHERE user_id = NEW.user_id)` would prevent garbage data from accumulating while still leaving final processing to admin review.

## Private storage bucket with public URL call

The schema creates the `deposit-proofs` bucket as private:

```sql
INSERT INTO storage.buckets (id, name, public)
VALUES ('deposit-proofs', 'deposit-proofs', FALSE)
```

But `deposit_screen.dart` retrieves the URL with:

```dart
final publicUrl = SupabaseService.client.storage
    .from('deposit-proofs')
    .getPublicUrl(fileName);
```

For private buckets, `getPublicUrl` returns a URL that Supabase will serve with a 403. The code should use `createSignedUrl(fileName, Duration(...))` and store the path (signing on read), or make the bucket public. As written, deposit proof images are never viewable after upload.

## Checkout atomicity gap

`placeOrder` in `shop_provider.dart` performs two sequential inserts:

```dart
await SupabaseService.client.from('orders').insert({...});
await SupabaseService.client.from('order_items').insert(orderItems);
```

If the second insert fails, the order row persists with no items. The function returns `false` but doesn't delete the orphaned order. This should be an RPC call wrapping both in a transaction, or at minimum the order should be deleted in the catch block.

No stock validation exists — the products table has a `stock` column but nothing decrements it or checks availability before order placement. Two concurrent checkouts can oversell.

## Auth subscription leak

In `AuthNotifier._initialize()`:

```dart
SupabaseService.onAuthStateChange.listen((data) { ... });
```

The return value (a `StreamSubscription`) is never assigned to `_authSubscription`. The `dispose` method calls `_authSubscription?.cancel()` which is always null. If the notifier is ever recreated (hot restart, test teardown), the old listener continues firing on a disposed notifier.

## Hardcoded Supabase instance URL

```dart
static const String supabaseUrl = String.fromEnvironment(
  'SUPABASE_URL',
  defaultValue: 'https://npzomevhjdxbgbuojwoo.supabase.co',
);
```

This exposes the production Supabase project identifier in version control. The URL alone isn't catastrophic since RLS is in place, but it enables enumeration of public endpoints (storage buckets, REST API) and is unnecessary exposure. The default should be empty or a clearly-fake placeholder that forces the build to supply the secret.

## Admin seed FK constraint

The schema seeds:

```sql
INSERT INTO public.users (id, email, name, role, ...)
VALUES ('00000000-0000-0000-0000-000000000001', ...);
```

The `users.id` column has `REFERENCES auth.users(id) ON DELETE CASCADE`. Unless `auth.users` already contains this UUID (it won't for a fresh project), the insert fails with a foreign key violation. The commented-out block above it shows the correct approach (insert after real auth signup), but the uncommented live insert will break on first migration run.
