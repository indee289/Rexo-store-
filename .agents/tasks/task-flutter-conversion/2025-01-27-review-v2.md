# Flutter conversion — v2 review after fixes

The eight issues identified in v1 have been addressed in commit 1f40c0f. Column name mismatches are fixed, the auth subscription is properly disposed, the Supabase URL default is now empty, the admin seed is commented out, deposit proofs use signed URLs, the withdrawal trigger validates balance, and `placeOrder` cleans up orphaned orders. The ninth issue (zero test coverage) remains acknowledged but unaddressed.

This pass surfaces new concerns: the orphaned-order cleanup and notification deletion both call `.delete()` on tables with no RLS DELETE policy, meaning those operations silently do nothing; and no storage-level RLS policies exist for any bucket, so file uploads (avatar, deposit proof) will be rejected by Supabase Storage.

Watch for: order cleanup after failed order_items insert is dead code because RLS blocks the DELETE (confirmed); storage uploads to both public and private buckets will 403 due to missing `storage.objects` policies (confirmed); no stock decrement on checkout allows overselling (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Two RLS gaps remain after the v1 fixes. The `placeOrder` error handler calls `orders.delete()` but no DELETE policy exists on the orders table, so Supabase returns zero rows affected and the orphaned order persists — exactly the state the fix was meant to prevent. Notification deletion has the same gap.

The schema creates five storage buckets but defines zero `storage.objects` policies. Supabase Storage enforces RLS on the `storage.objects` table regardless of bucket visibility; without INSERT policies, the `uploadBinary` (deposit proofs) and `upload` (avatars) calls will receive a 403 response.

Checkout still performs no stock validation. The products table carries a `stock` column that nothing reads or decrements during order placement, allowing concurrent purchases to oversell.

## RLS DELETE gap in order cleanup

The v1 fix added error handling to `placeOrder`:

```dart
try {
  await SupabaseService.client.from('order_items').insert(orderItems);
} catch (e) {
  // Delete the orphaned order if order_items insert fails
  await SupabaseService.client.from('orders').delete().eq('id', orderId);
  rethrow;
}
```

The orders table has RLS enabled with SELECT, INSERT, and UPDATE policies but no DELETE policy:

```sql
CREATE POLICY "Users can create orders" ON orders
    FOR INSERT WITH CHECK (auth.uid() = user_id);
-- no FOR DELETE policy
```

When RLS is enabled and no matching policy exists for the operation, Supabase returns an empty result (zero rows deleted) rather than an error. The cleanup line executes without throwing, but the orphaned order persists. The `rethrow` propagates to the outer catch which returns `false`, so the user sees a generic failure while a dangling order remains in the database.

The same pattern applies to `notifications.delete()` — called from the UI's delete-notification action but blocked by RLS silently.

## Storage policies completely absent

The schema creates buckets:

```sql
INSERT INTO storage.buckets (id, name, public)
VALUES
    ('avatars', 'avatars', TRUE),
    ('deposit-proofs', 'deposit-proofs', FALSE),
    ...
```

But never creates policies on `storage.objects`. Supabase Storage uses its own RLS table (`storage.objects`) independent of the bucket's `public` flag for writes. Even public buckets require an INSERT policy for authenticated uploads. The `profile_provider.dart` avatar upload and `deposit_screen.dart` proof upload will both fail.

Required policies (example for avatars):

```sql
CREATE POLICY "Users can upload own avatar"
ON storage.objects FOR INSERT
WITH CHECK (bucket_id = 'avatars' AND auth.uid()::text = (storage.foldername(name))[1]);

CREATE POLICY "Anyone can read avatars"
ON storage.objects FOR SELECT
USING (bucket_id = 'avatars');
```

Similar scoped policies are needed for `deposit-proofs` (user uploads own, admin reads all) and other buckets.

## Stock validation gap on checkout

The products table includes `stock INTEGER NOT NULL DEFAULT 0`, but `placeOrder` never checks stock availability or decrements it:

1. User adds items to local cart (no reservation)
2. `placeOrder` inserts order row
3. `placeOrder` inserts order_items rows
4. Nothing reads or decrements `products.stock`

Two users purchasing the last unit simultaneously will both succeed, creating oversold inventory. A `BEFORE INSERT` trigger on `order_items` that decrements stock and raises an exception if `stock < quantity` would enforce this at the database level.
