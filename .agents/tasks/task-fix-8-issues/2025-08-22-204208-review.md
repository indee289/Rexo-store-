# Eight-issue batch fix: wallet crediting, KYC icons, campaign form, dark mode, realtime, creators, push docs, 2FA UI

This change addresses eight user-reported issues across a Flutter multi-app project (user app + admin app) backed by Supabase. The fixes range from data-integrity corrections (admin deposit/withdrawal approval now updates wallet balances) through UI consistency (KYC status icons, dark mode text contrast) to new feature work (creator profiles with follow/unfollow, realtime subscriptions, messaging stream). Two issues — push notifications and 2FA — are documented as unverifiable without device/server configuration, which is the honest and correct call.

Watch for: The wallet balance update in `approveDeposit`/`approveWithdrawal` uses a read-then-write pattern without server-side atomicity (confirmed) — concurrent admin approvals on the same user can produce a lost update. The realtime messages provider subscribes to all INSERT events on the messages table rather than filtering by the conversation participants (confirmed), which means it refetches on every message in the system if Postgres change filters aren't applied.

**Verdict**: NEEDS_CHANGES

## High-level view

The wallet crediting fix correctly fetches deposit/withdrawal metadata before updating the balance, and includes an insufficient-balance guard for withdrawals. However, the entire operation is a multi-step read-then-write executed from the client, with no server-side atomicity (no RPC, no transaction). Under concurrent load, two approvals for the same user can read the same stale balance and overwrite each other.

The campaign form is a clean rewrite with exactly the nine specified fields, theme-aware styling, and proper validation. The SQL migration adds the three new columns with appropriate CHECK constraints and updates the platform constraint to include 'facebook'.

Dark mode was fixed at the root — `AppTextStyles` no longer sets color at all (except `button` which keeps `Colors.white`), letting theme inheritance work. Several widgets across both apps were also patched to replace hardcoded `Colors.white` / `AppColors.secondary` backgrounds with `theme.colorScheme.surface`.

The realtime subscriptions for wallet and KYC use Supabase's `.stream()` API correctly, subscribing by primary key and filtering by `user_id`. The messages realtime provider takes a different (manual) approach via `onPostgresChanges` which works but has a filtering gap.

The creator profile and follow/unfollow system is well-structured: a follows table with appropriate RLS, a clean provider layer with invalidation on mutation, and a profile screen that wires follow state to the UI.

<summary>Issues (4)</summary>

1. **Wallet balance race condition** — `approveDeposit` and `approveWithdrawal` use client-side read-then-write without a transaction or Supabase RPC. Move to a Postgres function (`increment_balance(user_id, amount)`) or use `.rpc()` to guarantee atomicity.
2. **Realtime messages channel lacks row-level filter** — `chatMessagesStreamProvider` subscribes to ALL inserts on the messages table. Add a `filter` parameter (e.g., `filter: 'receiver_id=eq.${user.id}'`) or use `.stream(primaryKey: ['id']).eq(...)` like the wallet/KYC providers.
3. **Follow action has no duplicate-insert guard** — If `follow()` is tapped rapidly before the first request completes, two INSERT calls will fire. The UNIQUE constraint will cause a Postgres error, but the UI will briefly flash an error state. Add optimistic locking or disable the button during the request.
4. **Campaign form cover image not validated** — `_coverImageUrl` can remain `null` and the insert sends `''` (empty string). If a cover image is required by the product spec, add a validator. If optional, the empty-string sentinel may confuse downstream consumers expecting a URL or null.

## Wallet balance update without server-side atomicity

`approveDeposit` (admin_provider.dart) fetches the deposit record for `user_id` and `amount`, then fetches the wallet's `available_balance`, computes the new total client-side, and writes it back:

```dart
final currentBalance = (wallet['available_balance'] as num).toDouble();
await SupabaseService.client.from('wallets').update(
    {'available_balance': currentBalance + amount}).eq('id', walletId);
```

Between the read and the write, another admin action (or the same admin approving a second deposit for the same user) can read the same `currentBalance`, and whichever write lands last wins — the other deposit's credit is lost. This is a textbook lost-update race.

The same pattern exists in `approveWithdrawal` and the standalone `creditWallet`/`debitWallet` methods. The mitigation is a Postgres function: `SELECT increment_wallet_balance(p_user_id UUID, p_amount NUMERIC)` that does `UPDATE wallets SET available_balance = available_balance + p_amount WHERE user_id = p_user_id`, called via `.rpc()`. The insufficient-balance check for withdrawals can be a `CHECK (available_balance >= 0)` constraint on the column or a conditional in the function.

## Realtime messages subscription scope

The messages provider calls `SupabaseService.client.channel('messages_$otherUserId').onPostgresChanges(event: PostgresChangeEvent.insert, ...)` without a `filter:` argument. This means the Supabase Realtime server sends an event for every INSERT into the messages table, regardless of sender/receiver. The callback then refetches the full conversation. Under high message volume this generates unnecessary network traffic and database queries for messages unrelated to the open conversation.

Adding `filter: 'receiver_id=eq.${user.id}'` (or an OR filter on sender_id) would scope the subscription to relevant rows. Alternatively, switching to the `.stream(primaryKey: ['id']).eq(...)` pattern used successfully by the wallet and KYC providers would handle this transparently.

## Campaign form cover image sentinel

The `_coverImageUrl` field defaults to `null`. If the user doesn't upload an image, the insert sends `'cover_image_url': _coverImageUrl ?? ''` — an empty string rather than null. Downstream code (list cards, detail screens) that does `if (url != null && url.isNotEmpty)` will handle this correctly, but code that simply passes the URL to a network image widget without checking for empty will get a load error. Sending `null` instead of `''` would be more defensive.

## Follow action double-tap risk

`FollowActionsNotifier.follow()` does not guard against re-entry. If the user taps Follow twice quickly, both calls will attempt `INSERT INTO follows`. The `UNIQUE(follower_id, following_id)` constraint will reject the second, and the catch block will push an error state into the Riverpod provider. The UI handles the error state by showing a generic "Follow" button (from the `error:` branch of `isFollowingAsync.when`), causing a brief flash. A simple `if (state is AsyncLoading) return false;` guard at the top of `follow()` would prevent this.

## Potentially unused realtime providers

`depositsRealtimeProvider` and `withdrawalsRealtimeProvider` are declared in wallet_provider.dart but are not referenced anywhere in the diff. The transaction history screen still uses the `FutureProvider` `transactionsProvider`. If no screen consumes these stream providers, they are dead code that opens unnecessary Supabase Realtime channels when the provider system initializes them.

## Magic color in 2FA info box

The 2FA screen uses `const Color(0xFF2196F3)` (Material Blue) for the info box background and border since `AppColors.info` doesn't exist. This creates a one-off color outside the theme system that won't adapt to dark mode unless the opacity values happen to work in both contexts. Consider adding `AppColors.info` or using `theme.colorScheme.primaryContainer` to keep it within the theme.
