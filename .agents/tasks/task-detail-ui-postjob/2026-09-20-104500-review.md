## High-level view

Issue #3 is resolved and consistent with the job screen's pill: the campaign pill maps `active`/`open` → orange "Active", `closed`/`inactive` → grey "Closed", any other non-empty status passes through as its own text (orange), and a category label is used when status is empty. The color now keys off the normalized `isClosed` flag rather than being hardcoded orange.

The v1 fix, however, exposes a downstream asymmetry the campaign screen carried all along: the sticky bottom bar (`CampaignDetailBottomBar`) receives only `campaignId` and watches `hasApplied`. It has no access to `status` or slot counts, so its only non-apply state is "Already Applied". The job screen's `_ApplyBar`, by contrast, gates on applied, slots-full, and closed, showing a disabled neutral "Closed" button for a closed job. The result is a Closed campaign that displays a grey "Closed" pill up top and a fully-live orange "Apply Now" at the bottom — visually contradictory and letting users apply to a closed campaign.

The Post-a-Job fix is unchanged from v1 and behaves as designed: `createJob` writes a minimal legacy-safe column set with a positive `budget`, keeps `payout_model:'job'` as an insert value (never a query filter), and depends on `POST_JOB_FIX.sql` being run once to relax the remaining live constraints. The migration protects `id/title/description/brand_id/status` and is idempotent. The debug SnackBar suffix remains, as intended.

### Closed-campaign Apply CTA is not gated

The pill fix makes a latent inconsistency visible. `CampaignDetailBottomBar` is built at the scaffold level with just `campaignId`; it re-watches `hasAppliedProvider` and renders either an "Already Applied" status button or the orange `_ApplyNowButton` that pushes `/campaigns/$campaignId/apply`. It never sees the campaign's `status` or slot counts, even though both are computed in `_CampaignDetailScrollView` (`status`, `filled`, `total`) and the raw `campaign` map is in scope where the bottom bar is constructed (line 47).

The job screen threads all of this through `_ApplyBar(jobId, job, hasApplied, isFull, isClosed)` and `_buildButton()` returns a disabled neutral "Closed" `_StatusButton` for the closed case (and a red "Slots Full" for the full case). The campaign screen has the equivalent `_StatusButton` widget but only ever uses it for "Already Applied". So a closed campaign presents contradictory affordances — "Closed" in the header, "Apply Now" at the bottom — and the tap still routes into the apply flow. Pass the normalized closed state into the bottom bar and short-circuit to the disabled "Closed" button; mirroring the job screen's slots-full gate would close the parallel gap.

### Post-a-Job invariants re-confirmed

`payout_model:'job'` is written as an insert value only; there is no `.eq/.neq('payout_model', …)` filter anywhere under `lib/` (the only textual hits are comments), and jobs-vs-campaigns discrimination stays client-side via `.where`. Insert keys round-trip with `_mapCampaignToJob` (`payout_per_creator`↔`payment_amount`, `slots`↔`max_slots`). The insert still depends on `POST_JOB_FIX.sql` being run once to relax live constraints; the migration protects `id/title/description/brand_id/status` and is idempotent. This SQL dependency (Issue #1) and the `[debug]` SnackBar suffix (Issue #2) are accepted, intentional decisions, not blockers on this pass.
