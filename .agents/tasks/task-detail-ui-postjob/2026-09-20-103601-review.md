# Premium Job & Campaign detail screens + Post-a-Job insert fix (v1)

Rewrites the Job Details and Campaign Details screens to the premium reference mockups (cover + status pill, payment/stat cards with the big orange amount, stateful Read more/less, "What to submit" chips, sticky orange Apply CTA) and hardens job creation against a quirky legacy `campaigns` table. `createJob` now sends a minimal, legacy-safe column set with a positive `budget`, keeps `payout_model:'job'` as an insert *value* (never a query filter), and ships an idempotent `supabase/POST_JOB_FIX.sql` that relaxes stray NOT-NULL / CHECK constraints. A temporary raw-error debug string is appended to the Post-a-Job failure SnackBar to diagnose the constraint that was rejecting inserts.

**Watch for:** the Post-a-Job error is only fully resolved once `POST_JOB_FIX.sql` is run in the Supabase SQL editor — the Dart change alone reduces but does not guarantee a successful insert (confirmed). A raw-error `[debug]` suffix is shipped to end users in the failure SnackBar and must be removed before release (confirmed). The campaign cover pill renders orange even for a "Closed" campaign, unlike the job screen which greys it out (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The two detail screens are full rewrites that read the *same* provider keys as before — no provider signatures changed, and job-shaped keys (`payment_amount`, `max_slots`, `cover_image_url`, `deadline`, `created_at`, `status`) still flow through `_mapCampaignToJob`. Both screens gate every text/icon/surface color on `Theme.brightness` using AppColors dark/light tokens; the only hardcoded whites sit on the cover overlay and inside the orange CTA, where they are correct in both themes. The big money figure and the Apply Now CTA use `AppColors.accentOrange` (#FB923C) on both screens, matching the reference. Read more/less is genuinely stateful — a `TextPainter` measures overflow and a `setState` toggle expands the text.

The Post-a-Job fix is two-part and both parts are required. The Dart `createJob` insert was trimmed to a minimal, confidently-present column set and now writes a positive `budget` instead of `0`; `payout_model:'job'` stays as a row value, which is allowed (PostgREST only rejects `.eq/.neq` *filters* on that column, and none exist in `lib/`). The companion SQL migration relaxes every remaining non-essential NOT-NULL and drops CHECK constraints on `payout_model`/`payoutModel`/`platform`, protecting `id/title/description/brand_id/status`. Because the constraints live in the live database, the insert can still fail until the SQL is run manually.

The debug instrumentation in `post_job_screen.dart` is deliberate and time-boxed with a `// TODO(remove-debug)`, but as written it surfaces raw backend error text to the end user, which should not reach production.

### Post-a-Job fix: Dart insert vs. the SQL migration

The failure the user reported ("Something went wrong. Please try again.") comes from an INSERT into the legacy `public.campaigns` table being rejected by constraints the app can't see. `createJob` now computes `budget = payout > 0 ? payout : 1` so the row survives any `budget > 0` CHECK or NOT-NULL, and drops the camelCase `createdAt` write (sending only snake_case `created_at`). This removes the *known* failure modes only — the residual NOT-NULL-without-default columns and CHECK constraints on the live table are relaxed solely by `POST_JOB_FIX.sql`. Until that script is run in the Supabase SQL editor (and PostgREST reloads its cache ~10s later), the insert can still fail. The migration is idempotent (per-statement exception handling, `DROP ... IF EXISTS`, a re-run matches nothing) and protects `id/title/description/brand_id/status` while relaxing everything else.

`payout_model:'job'` is written as an insert value, not a filter — verified there is no `.eq('payout_model', ...)`/`.neq(...)` server-side filter anywhere under `lib/` (the only textual hit is a comment). All jobs-vs-campaigns discrimination is done client-side via `.where((row) => row['payout_model'] == 'job')`, so the project invariant holds.

### Debug string in the Post-a-Job SnackBar

`post_job_screen.dart` appends `\n[debug] <raw error, truncated to 300 chars>` after the sanitized message whenever the action has an error. It is explicitly marked `// TODO(remove-debug)` and is useful right now to pinpoint the failing column, but it routes raw backend error text to the end-user-facing SnackBar. This needs to come out before the build ships; the sanitized message alone is the correct production UX.

### Campaign cover pill color inconsistency

In the campaign `_CoverHeader`, the pill background is `AppColors.accentOrange` regardless of `pillText` — including when the status resolves to `'Closed'`. The job screen's cover pill correctly switches to `AppColors.neutral` for the closed state. The result is an orange "Closed" badge on closed campaigns, which is visually wrong and inconsistent between the two screens. Gate the campaign pill color on the resolved status the way the job screen does.

</details>
