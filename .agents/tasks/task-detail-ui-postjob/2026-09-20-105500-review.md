# Campaign Apply CTA now gated on closed/full state (v3)

Final review pass after the coder addressed the single v2 blocker. That blocker — a Closed campaign showing a greyed "Closed" cover pill up top but a fully-live orange "Apply Now" at the sticky bottom bar — is now fixed (commit `236b95e`). `CampaignDetailScreen.build` computes a normalized `isClosed` (status ∈ {closed, inactive}) and `isFull` (`total_slots > 0 && filled_slots >= total_slots`) from the in-scope campaign map and threads both into `CampaignDetailBottomBar`, which short-circuits before `hasApplied.when(...)` to render a disabled neutral "Closed" `_StatusButton` or a red "Slots Full" one. This mirrors the Job Details `_ApplyBar` gate, so the header pill and the bottom CTA now agree, and a closed/full campaign no longer routes into the apply flow. All prior invariants re-confirmed: no server-side `.eq/.neq('payout_model')` filter under `lib/` (only client-side `.where` and comments), no provider signature changes, dark-mode-safe colors, orange for the money figure and both Apply CTAs, and a genuinely stateful Read more/less on both screens.

**Watch for:** the two bottom bars evaluate their gates in a different order — the job bar checks `hasApplied` first then full/closed, while the campaign bar checks closed/full first then applied — so a closed item you already applied to reads "Already Applied" on the job screen but "Closed" on the campaign screen (possible; cosmetic only, both still block re-apply).

**Verdict**: APPROVED

## High-level view

The v2 blocker is resolved and the two detail screens are now behaviorally symmetric on the apply gate: a closed/inactive item shows a disabled neutral "Closed" button, a slot-full item a disabled red "Slots Full" button, and only a genuinely open item exposes the live orange "Apply Now". The campaign screen derives the gate flags from the same `status`/`filled_slots`/`total_slots` fields the header pill uses, so pill and CTA can no longer contradict each other.

The reference-UI work matches the mockups: job details carry the orange Payment figure with "Per approved submission", a Slots line rendering "N of M slots left" (or "Slots Full"/"Unlimited"), and the "What to submit" chips; campaign details carry the two stat cards (orange Budget "Per creator", Slots "Creators needed"), the brand row, pills, and "About Campaign" with a working Read more. Both money figures and Apply CTAs use `accentOrange`.

The Post-a-Job path is unchanged from v1/v2 and behaves as designed: `createJob` writes a minimal legacy-safe column set with `payout_model:'job'` as an insert value (never a query filter) and a positive `budget`, depending on the idempotent `POST_JOB_FIX.sql` being run once to relax the remaining live constraints. That SQL dependency (Issue #1) and the `[debug]` SnackBar suffix (Issue #2) are accepted, intentional decisions — not blockers.

The only new observation is cosmetic: the two bottom bars order their gate checks differently, producing a different (but equally non-actionable) label for the rare closed-and-already-applied case.

### Closed/full campaign CTA is now gated (v2 blocker resolved)

`CampaignDetailScreen.build` reads `status`, `filled_slots`, and `total_slots` off the resolved campaign map — the same fields the cover pill normalizes — and passes `isClosed`/`isFull` into `CampaignDetailBottomBar`. The bottom bar's `_buildButton` short-circuits on those flags before touching `hasApplied`:

```
if (isClosed) return _StatusButton(label: 'Closed',     icon: Iconsax.slash, color: AppColors.neutral);
if (isFull)   return _StatusButton(label: 'Slots Full', icon: Iconsax.slash, color: AppColors.error);
return hasApplied.when(... Already Applied / Apply Now / loading ...);
```

This matches the Job Details `_ApplyBar._buildButton`, which also returns disabled `_StatusButton`s for the full and closed states and the orange `_ApplyNowButton` only when open. The header pill and the CTA are now driven off the same normalized status, so the earlier contradiction (grey "Closed" pill + live orange "Apply Now") is gone and the tap no longer routes to `/campaigns/$id/apply` for a closed or full campaign.

The one residual difference is the order of the checks. `_ApplyBar` evaluates `hasApplied → isFull → isClosed`; `CampaignDetailBottomBar` evaluates `isClosed → isFull → hasApplied`. For a closed campaign the user already applied to, the job screen would say "Already Applied" and the campaign screen "Closed". Both outcomes correctly prevent a second apply, so this is a label-parity nit, not a functional gap.

### Post-a-Job insert path re-confirmed

`createJob` sends only the columns the insert needs — `title/description/category/payout_per_creator/slots/deadline/cover_image/payout_model/brand_id/brandName/status/budget/created_at/updated_at` — with `payout_model:'job'` written as a row value and `budget` set to the positive payout (min 1) to survive any CHECK/NOT-NULL constraint. There is no `.eq/.neq('payout_model', …)` filter anywhere under `lib/`; the only textual hits are explanatory comments, and jobs-vs-campaigns discrimination stays client-side via `.where`. The insert still depends on `POST_JOB_FIX.sql` (idempotent, protects `id/title/description/brand_id/status`) being run once — Issue #1, accepted. The raw-error `[debug]` suffix on the failure SnackBar remains `// TODO(remove-debug)`-marked — Issue #2, accepted.
