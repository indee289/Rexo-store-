# Forced PostgREST schema-cache rebuild via DDL events for the PGRST205 jobs/banners failure (v1)

Two new files ship a fresh attack on the stuck PostgREST cache that keeps the Jobs and Banners screens throwing `PGRST205 Could not find the table 'public.jobs' in the schema cache`. `supabase/FORCE_SCHEMA_RELOAD.sql` abandons the plain-`NOTIFY` approach that already failed and instead emits real DDL on the exposed `public` schema — a `COMMENT ON SCHEMA` plus a create/drop of a disposable throwaway table (`public._pgrst_cache_bust`) — so PostgREST's DDL event triggers fire a full cache rebuild, then closes with the two `NOTIFY pgrst` reloads as a belt-and-suspenders. `supabase/PGRST205_RUNBOOK.md` is a short Hinglish runbook that walks a non-technical user through running the SQL, then the Dashboard fallbacks. The Flutter data-access layer is untouched, matching the working `campaigns` `.from()` path exactly.

Watch for: the DDL-event method only forces a rebuild if the project's PostgREST DDL event triggers (`pgrst_ddl_watch`/`pgrst_drop_watch`) are installed — Supabase installs them by default, so this is **likely** fine, but if a prior migration dropped them the DDL path is inert and the fix collapses back to the same `NOTIFY` that already failed (possible). No functional risk in the change itself; it is idempotent, safe to re-run, and touches no real tables or `.dart` code (confirmed).

**Verdict**: APPROVED

## High-level view

The core bet is that a *real* DDL event is a stronger cache-invalidation signal than `NOTIFY` alone. On Supabase, PostgREST ships event triggers on `ddl_command_end` and `sql_drop` that watch the exposed schema; `COMMENT ON SCHEMA public` and the create-then-drop of a throwaway table are chosen precisely to fire those. This is a genuinely different mechanism from the prior `RELOAD_SCHEMA_CACHE.sql`, which only issued `NOTIFY`/`pg_notify` — so the "try a different method" requirement is met.

The one soft spot is the dependency on the DDL event triggers existing. The file presents the DDL path as the primary fix and `NOTIFY` as backup, but if those triggers were ever dropped, the primary path does nothing and the user is back to the failing `NOTIFY`. The embedded Dashboard fallbacks (Exposed-schemas toggle, then Restart) are the real safety net for that case.

### DDL events as a stronger signal than NOTIFY

The prior `RELOAD_SCHEMA_CACHE.sql` did nothing but `NOTIFY pgrst, 'reload schema'` and `SELECT pg_notify('pgrst', 'reload schema')`, and that did not clear the stuck cache. This file changes the mechanism: it triggers actual DDL on the exposed schema so PostgREST's schema-watch event triggers fire.

```sql
COMMENT ON SCHEMA public IS 'reload schema';
DO $$
BEGIN
  DROP TABLE IF EXISTS public._pgrst_cache_bust;
  CREATE TABLE public._pgrst_cache_bust (x int);
  DROP TABLE public._pgrst_cache_bust;
END $$;
```

On a standard Supabase project, PostgREST installs `ddl_command_end` and `sql_drop` event triggers that call `pgrst_ddl_watch()` / `pgrst_drop_watch()`; both the schema comment and the create/drop are DDL that fire them. The caveat: this path is only stronger than `NOTIFY` *if* those triggers exist. If they were ever dropped by an earlier migration, the `COMMENT` and create/drop become cache no-ops and the file degrades to the same two `NOTIFY` statements that already failed. Supabase installs them by default (likely fine), but it is the single assumption the whole DDL approach rests on, and it is not asserted or checked anywhere in the script.

### Idempotency and blast radius

The throwaway table is created and dropped inside one `DO` block, with a leading `DROP TABLE IF EXISTS` to clean up a half-completed prior run. Nothing accumulates across runs and nothing outside `_pgrst_cache_bust` is written. A grep for any drop of the real tables returns zero matches, and the real `jobs`/`job_applications`/`banners` objects are never named in an executable statement. `$$` delimiters balance (count 2), and the file's last two executable statements are the two `NOTIFY` reloads in the required order.

### Dashboard fallbacks and the runbook

The embedded Option B (Exposed-schemas remove `public` → Save → 30s → re-add → Save → 60s) and Option C (Settings → General → Restart project) match current Supabase Dashboard layout and are the correct escalation path — toggling the exposed schema forces PostgREST to re-read config and rebuild, and a restart is the nuclear option. The runbook mirrors these steps in the same order, is written in clear Hinglish, sets realistic free-tier timing expectations, and states success concretely (real jobs/banners load, no DBG3/PGRST205). These fallbacks are what actually cover the DDL-trigger-missing case, which makes them more than documentation — they are the real safety net.

### Flutter layer deliberately unchanged

`git status --porcelain` shows only the two new `supabase/` files plus task-state; no `.dart` file is modified and `error_utils.dart` is untouched. The providers still call `SupabaseService.client.from('jobs' | 'job_applications' | 'banners')` (jobs provider lines 25–169, banners provider lines 9–78), identical to the `campaigns` path that already works. The failure is server-side cache, not client code, so leaving the data-access layer alone keeps the fix surface minimal.
