# Fix pass for Supabase insert DTOs and admin error surfacing

This is the v2 review after the five issues identified in the first pass were addressed. The campaign_applications INSERT now supplies all NOT NULL columns with a correct status value. Both `ensureUserProfile` and `ensureWallet` use upsert with `onConflict`. Admin approve/reject actions surface errors via `AdminUiState.actionError` displayed as a dismissible banner. `WithdrawalInsertDto.payout_details` uses `JsonObject` for JSONB compatibility, and `DepositInsertDto` includes `id` and `brand_name`.

Watch for: The wallets and users tables have no INSERT RLS policy in `020_restore_secure_rls.sql`, so both `ensureWallet` and `ensureUserProfile` upserts will be denied at the database level for non-admin users (confirmed). This makes the auto-provisioning logic inert in any Supabase project with RLS enabled.

**Verdict**: NEEDS_CHANGES

## High-level view

The outstanding gap is the database permission layer: `020_restore_secure_rls.sql` defines no INSERT policy on `users` or `wallets` for authenticated users. Since Supabase enforces RLS by default, the client-side upsert will be rejected with a `42501` permission denied error — which the code silently catches and returns null, leaving the user on "Profile not found" or a zero-balance wallet screen with no recovery path. The Kotlin-side fixes are correct in isolation, but they cannot execute against a production Supabase instance without the missing policies.

## RLS gap blocks user/wallet auto-provisioning

The `ensureUserProfile` upsert targets the `users` table and `ensureWallet` targets `wallets`. With RLS enabled (which `020_restore_secure_rls.sql` does via `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`), any operation not covered by an explicit policy is denied. The current policies:

```
-- users: SELECT(own), UPDATE(own), SELECT(admin), UPDATE(admin), DELETE(admin)
-- wallets: SELECT(own), SELECT(admin), UPDATE(admin)
```

Neither table has an INSERT policy. When a new user signs up and `ensureUserProfile` runs, the upsert hits RLS and fails. The code catches the exception and returns null, so `ProfileViewModel` transitions to `ProfileState.Empty` — displaying "Profile not found" with no user-visible error message explaining why.

The fix is two INSERT policies in a new migration:

```sql
CREATE POLICY "Users can create own profile" ON users
  FOR INSERT WITH CHECK (auth.uid()::text = id);

CREATE POLICY "Users can create own wallet" ON wallets
  FOR INSERT WITH CHECK (auth.uid()::text = user_id);
```

Without these, the entire auto-provisioning logic is inert in production. The failure mode is fail-closed (RLS denies the operation) rather than fail-open, so there's no security risk — just broken functionality for every new user.
