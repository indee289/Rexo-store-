# Premium UI overhaul and Supabase auto-provisioning

This change rewrites the visual layer of the Rexo Marketplace Android app from glassmorphic cards to a clean white surface-and-border style, while fixing the Supabase data pipeline so new users get wallet and profile rows auto-created on first access. A floating pill-style bottom navigation replaces the Material3 NavigationBar. The Admin panel was rebuilt from scratch with its own ViewModel that fetches real pending KYC, deposits, withdrawals, and user data. A PrivacyPolicyScreen was added with hardcoded content and wired into the nav graph.

Watch for: The `ensureWallet` insert will fail at runtime if Supabase has RLS policies that block INSERT from the client-side anon key without a matching policy on `wallets` (confirmed — no RLS policy for client-side wallet creation is in `schema.sql`). The `campaign_applications` insert is missing ~6 NOT NULL columns required by the schema and will throw a Postgres constraint error when a user taps "Apply" (confirmed). Admin approve/reject actions silently swallow exceptions, making failures invisible to the operator (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The CampaignRepository was decoupled from its DAO constructor parameter and now accesses `SupabaseClient` as a singleton directly, letting CampaignViewModel use a default no-arg constructor. This tightens coupling to the singleton, making the data layer untestable without an initialized Android context — consistent with the rest of the project but accumulating tech debt.

Profile and Wallet screens now auto-provision rows for new users via `ensureUserProfile` and `ensureWallet`. Both use check-then-insert rather than upsert, so they race under concurrent access and neither accounts for RLS policies that would gate INSERT permission.

The `campaign_applications` INSERT sends only `campaign_id`, `proposal`, and `status`, but the schema declares `campaign_title`, `brand_name`, `creator_id`, `creator_name`, `creator_handle`, and `fee_requested` as NOT NULL. This will always fail at the database level.

The Admin panel's approve/reject methods catch and discard all exceptions. If a status update fails, the admin sees the list reload without knowing whether the action succeeded.

The floating pill navigation's active-tab click handler is a no-op `{}` — tapping the already-selected tab can't scroll-to-top or refresh.

## Auto-provisioning with check-then-insert

`UserRepository.ensureUserProfile` and `WalletRepository.ensureWallet` both follow the same pattern: SELECT the row, if null INSERT a new one, then SELECT again to return it.

First failure mode — a race: if ProfileScreen and another component both call `ensureUserProfile` simultaneously before the row exists, both pass the `existing == null` check and both attempt INSERT. The `users` table has a PRIMARY KEY on `id`, so the second insert throws a unique violation — caught and returns null, causing the profile screen to show "Profile not found" intermittently.

```kotlin
// Current pattern (race-prone):
val existing = getUser(userId)
if (existing != null) return@withContext existing
SupabaseClient.client.from("users").insert(newUser)

// Safer pattern:
SupabaseClient.client.from("users").upsert(newUser) {
    onConflict = "id"
}
```

Second failure mode — RLS: if the production Supabase project has RLS enabled (default for new projects), the anon key will be denied INSERT on `wallets` and `users` unless an explicit policy exists. The code catches this as a generic exception and returns null — the user sees an error state with no recovery path.

## campaign_applications schema mismatch

The `applyToCampaign` method inserts only three fields:

```kotlin
mapOf(
    "campaign_id" to campaignId,
    "proposal" to proposal,
    "status" to "pending"
)
```

The `campaign_applications` table requires these NOT NULL columns without defaults:
- `id` (PRIMARY KEY — VARCHAR, not auto-generated)
- `campaign_title`
- `brand_name`
- `creator_id`
- `creator_name`
- `creator_handle`
- `fee_requested`

This insert will always fail with a constraint violation. The status value `"pending"` also doesn't match the CHECK constraint which allows only `'submitted', 'approved', 'rejected', 'paid'`. This was pre-existing code only syntactically modified in this diff (singleton access change), but it's now actively relied upon by the new CampaignsScreen "Apply Now" button — making it a user-facing bug.

## Admin action error handling

All six admin action methods follow this pattern:

```kotlin
fun approveKyc(kycId: String) {
    viewModelScope.launch {
        try {
            withContext(Dispatchers.IO) { /* update */ }
            loadAdminData()  // reload list
        } catch (e: Exception) { /* ignore */ }
    }
}
```

If the update fails (network timeout, permission denied, row already processed), the admin gets no feedback. The list reloads showing the same pending state, and the admin may repeatedly tap approve with no effect. Surface a transient error message in `AdminUiState`.

## Pre-existing deposit/withdrawal insert gaps

The `deposits` and `withdrawals` tables use `id VARCHAR(255) PRIMARY KEY` — meaning inserts need an `id` to be supplied. The pre-existing `DepositInsertDto` and `WithdrawalInsertDto` omit `id` (and `deposits` also omits `brand_name` NOT NULL). This means the new Wallet UI's "Add Money" and "Withdraw" buttons will fail at the database level. Not introduced by this diff, but surfaced to users through the rebuilt Wallet screen.

## payout_details type mismatch

`WithdrawalInsertDto.payout_details` is typed `String` but the schema declares `payout_details JSONB NOT NULL DEFAULT '{}'::jsonb`. The Wallet UI's withdraw dialog collects payout details as free-form text. If the user enters something like "UPI: user@paytm" (not valid JSON), Supabase Postgrest will reject the insert with a JSON parse error. Pre-existing but now user-facing through the new withdrawal flow.
