# Dark mode, error propagation, and UI polish across User and Admin apps

This change makes the User App fully dark-mode-aware (shimmer widgets, profile badges, system UI overlay, bottom nav), improves error handling for profile edits by surfacing the actual Supabase error through `ErrorUtils.sanitize`, adds a fallback query for the "Top Creators" section when `creator_profiles` is empty, halves the splash screen delay, and adds a full dark theme plus settings provider to the Admin App. The UI polish pass enhances empty/error states with animations and retry buttons, tightens campaign card entrance animation, and fixes campaign search field visibility in dark mode.

Watch for: the `trendingCreatorsProvider` fallback query returns a different shape than the primary query (confirmed), and the `ProfileNotifier._lastError` field is mutable state accessed outside the notifier's state machine without synchronization (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The shimmer widgets were extracting colors from `AppColors` constants, which meant they were always light-mode. All seven shimmer classes now branch on `Theme.of(context).brightness` at build time. The same approach replaces the hardcoded `Colors.white` in profile avatar badge borders with `theme.colorScheme.surface`, and removes the forced `Brightness.dark` / `Brightness.light` from `SystemChrome`, letting the `AppBarTheme` drive status bar icon color.

Profile edit error handling threads the raw exception object through a new `_lastError` getter on `ProfileNotifier` so the UI can call `ErrorUtils.sanitize` with the actual error rather than showing a generic message. This introduces a side-channel field outside the notifier's `state`—meaning `lastError` won't trigger rebuilds and depends on timing relative to the `updateProfile` call.

The "Top Creators" fallback queries the `users` table (filtering `role='creator'`) when `creator_profiles` returns empty. The `CreatorCard` widget will receive a flat user map instead of the nested `{ *, users!inner(name, avatar_url, handle) }` structure, so downstream field access will either throw or silently produce nulls.

The Admin App gained a `SettingsNotifier` backed by `SharedPreferences` and a full dark theme. Because `_loadSettings` is async from the constructor, there's a brief theme flash on cold start if the persisted theme differs from the default.

The empty and error states on the home screen now have icon containers, animated fade-in + scale, and a bordered Retry button—but the retry button invalidates fewer providers than pull-to-refresh, creating a behavioral asymmetry.

## Trending creators fallback data shape mismatch

The primary query in `trendingCreatorsProvider`:

```dart
.from('creator_profiles')
.select('*, users!inner(name, avatar_url, handle)')
```

returns objects shaped like `{ followers: ..., users: { name: ..., avatar_url: ..., handle: ... } }`. The fallback:

```dart
.from('users')
.select()
.eq('role', 'creator')
```

returns flat user rows: `{ id, name, avatar_url, handle, role, … }`. If `CreatorCard` accesses nested `creator['users']['name']`, the fallback path throws a `NoSuchMethodError` (calling `[]` on null) or renders blank fields. The provider does not normalize the data before returning it.

The fix is either to wrap the fallback rows into the same nested structure (`{ 'users': { 'name': row['name'], … }, 'followers': 0 }`) or to have `CreatorCard` detect the shape and read from the appropriate level.

## ProfileNotifier `_lastError` as out-of-band state

`ProfileNotifier` extends `StateNotifier<AsyncValue<void>>`. The new `_lastError` field is set inside the `catch` block and read by the UI immediately after `updateProfile` returns `false`:

```dart
final errorMessage = notifier.lastError != null
    ? ErrorUtils.sanitize(notifier.lastError)
    : 'Failed to update profile';
```

The current call site works because the read happens synchronously after `await updateProfile(...)` within the same `onPressed` callback. But `lastError` isn't cleared until the _next_ call to `updateProfile`, so a widget that mounts later and reads it will see a stale error. A cleaner API would return the error from `updateProfile` directly (e.g., `Future<String?> updateProfile(…)` returning null on success) so the caller doesn't reach into internal notifier state.

## Retry button provider asymmetry

The error state retry button invalidates `featuredCampaignsProvider`, `trendingCreatorsProvider`, and `recentCampaignsProvider`. The `RefreshIndicator.onRefresh` also invalidates `homeUserProfileProvider`. A user whose greeting broke and taps Retry will not see it recover—they'd need to pull-to-refresh instead. Adding `homeUserProfileProvider` to the retry handler restores consistency.

## Admin settings persistence race

`SettingsNotifier._loadSettings` is async from the constructor. Between construction and completion, state is `const SettingsState()` (system theme). If SharedPreferences has "dark" stored, the app renders one frame in system-mode before snapping to dark—a visible theme flash. The standard mitigation is initializing `SharedPreferences` in `main()` and passing the instance to the notifier constructor, avoiding the async gap entirely.
