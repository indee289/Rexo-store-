# Dark mode, error propagation, and UI polish across User and Admin apps

This change makes the User App fully dark-mode-aware (shimmer widgets, profile badges, system UI overlay, bottom nav), improves error handling for profile edits by surfacing the actual Supabase error through `ErrorUtils.sanitize`, adds a fallback query for "Top Creators" when `creator_profiles` is empty, halves the splash screen delay, and adds a full dark theme plus settings provider to the Admin App. The UI polish pass enhances empty/error states with animations and retry buttons, tightens campaign card entrance animation, and fixes campaign search field visibility in dark mode.

Watch for: `ProfileNotifier._lastError` as a side-channel field outside the notifier's state machine—stale errors may confuse future widget reads (likely). Admin theme flash on cold start from async `SharedPreferences` in constructor (likely).

**Verdict**: APPROVED

## High-level view

The two blocking issues from the v1 review are resolved. The trending creators fallback now maps flat user rows into the nested `{ 'users': { ... }, 'followers': 0, 'user_id': ... }` shape expected by `CreatorCard`. The retry button invalidates all four providers, matching pull-to-refresh exactly.

`ProfileNotifier._lastError` remains a mutable field outside `AsyncValue<void> state`. The current call site works because `lastError` is read synchronously after the `await updateProfile(...)` returns `false`—but any widget mounting later will see stale error state. Not blocking for this change since the usage is tightly scoped to the `onPressed` callback.

The Admin App `SettingsNotifier` loads persisted preferences asynchronously from its constructor, so there's a single frame of default theme before the stored preference applies. For a v1 admin app this is acceptable; for production, initialize `SharedPreferences` in `main()` and pass it to the notifier.

Seven shimmer widget classes each independently compute the same three colors based on brightness. The duplication is harmless today but invites drift—if the dark shimmer palette changes, all seven classes need updating in lockstep.

## `_lastError` lifecycle and stale state

`ProfileNotifier` extends `StateNotifier<AsyncValue<void>>`. The `_lastError` field is set in the `catch` block and cleared at the start of the next `updateProfile` call:

```dart
_lastError = null;
// ... attempt update
} catch (e, st) {
  _lastError = e;
```

The consuming code in `edit_profile_screen.dart` reads it immediately after the failed await:

```dart
final errorMessage = notifier.lastError != null
    ? ErrorUtils.sanitize(notifier.lastError)
    : 'Failed to update profile';
```

This works because the read is synchronous in the same microtask as the `updateProfile` return. The risk is that a future refactor (or a different screen) calls `ref.read(profileNotifierProvider.notifier).lastError` at an unrelated point in time and receives a stale error from a previous operation. A safer API would be `Future<String?> updateProfile(...)` returning null on success and a sanitized message on failure, keeping the error co-located with the call site rather than ambient on the notifier.

## Admin settings initialization race

```dart
class SettingsNotifier extends StateNotifier<SettingsState> {
  SettingsNotifier() : super(const SettingsState()) {
    _loadSettings(); // async fire-and-forget
  }
```

Between construction and `_loadSettings` completion, `state` is `const SettingsState()` (themeMode: system). If SharedPreferences has `dark` stored, the MaterialApp renders one frame in system mode before snapping to dark. The standard fix: await `SharedPreferences.getInstance()` in `main()`, pass the instance to `SettingsNotifier`, and read synchronously in the constructor.
