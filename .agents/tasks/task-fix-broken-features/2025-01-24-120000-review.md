# Dark mode, language feedback, profile persistence, subscriptions hardening, admin profile & campaign creation, 2FA theming, and app icon replacement

This set of changes addresses a broad sweep of broken or missing features across both the user app and admin app. The primary approach is: replace hardcoded `AppColors.*` references with `Theme.of(context)` lookups to make dark mode functional; add try/catch around Supabase queries that fail when tables don't exist; persist avatar URLs during profile edits; add a campaign-creation FAB and a profile tab to the admin app; provide language-selection feedback with a "coming soon" note for Hindi; and replace the stock orange launcher icons with Rexo-branded PNGs at all mipmap densities.

Watch for: The campaign creation dialog inserts rows without associating them to the admin user (confirmed). The admin profile screen uses hardcoded `AppColors` throughout, contradicting the dark-mode fix applied to every other screen in this diff (confirmed). The subscriptions provider silently swallows all errors including auth failures, making debugging production issues difficult (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Dark mode now works end-to-end: `app.dart` reads `settings.themeMode` from a Riverpod provider backed by SharedPreferences, and seven screens were converted from static `AppColors` constants to `theme.colorScheme.*` lookups.

The subscription providers wrap their Supabase calls in try/catch and return empty lists on failure, plus the screen shows an improved empty state. This prevents crashes when the `subscription_plans` table doesn't exist or RLS blocks access, but the error-swallowing pattern means legitimate auth or network errors disappear silently.

Admin campaign creation is a dialog triggered by a FAB. It inserts directly into the `campaigns` table with no `created_by` or `brand_id` field, which means campaigns created by admin are orphaned rows with no ownership trail.

The admin profile screen is new: it shows the admin's name, email, role badge, and a sign-out button. It's the only screen in this diff that still uses hardcoded `AppColors` for text and background, which will render incorrectly in dark mode.

## Campaign creation without ownership

The admin campaign creation dialog (`campaign_control_screen.dart`) builds an insert map with `title`, `description`, `budget`, `platform`, `status`, and `created_at`. Notably absent is any user/admin identifier:

```dart
await SupabaseService.client.from('campaigns').insert({
  'title': titleController.text,
  'description': descriptionController.text,
  'budget': budget,
  'platform': selectedPlatform,
  'status': 'active',
  'created_at': DateTime.now().toIso8601String(),
});
```

If the `campaigns` table has a `created_by` or `brand_id` column with a NOT NULL constraint, this insert will fail silently (no error handling wraps it beyond the null-check on title/budget). If the column is nullable, the campaign exists but is unattributable. No error feedback reaches the admin user — the dialog just closes on success or remains open with no message on failure. The absence of a try/catch means a Postgres error propagates as an unhandled exception.

## Admin profile screen dark-mode gap

Every other screen modified in this diff follows the pattern `final theme = Theme.of(context)` and then uses `theme.scaffoldBackgroundColor`, `theme.colorScheme.onSurface`, etc. The new `AdminProfileScreen` does not — it references `AppColors.background`, `AppColors.textPrimary`, and `AppColors.textSecondary` directly across its entire build method. In dark mode, this produces light-colored backgrounds and text colors that don't adapt, rendering the screen illegible.

## Subscriptions error swallowing

Both `subscriptionPlansProvider` and `userSubscriptionsProvider` now catch all exceptions and return empty lists:

```dart
} catch (e) {
  // Return empty list on error (e.g., table doesn't exist or RLS issue)
  return [];
}
```

This silences auth token expiry, network timeouts, and malformed responses alongside the intended case of a missing table. The user sees "No plans available yet" with no way to distinguish "plans haven't been created" from "something is broken." A narrower catch (e.g., only `PostgrestException` with specific codes) or at least a `debugPrint(e)` would preserve debuggability without crashing the UI.
